# Known issues

Open problems in code already on `main`. Each has an ID, what it blocks, and the fix agreed so far.

**Read this before working on `backend/atlas/audit/`, `backend/atlas/egress/` or `deploy/`.** Close an issue by fixing it on a branch, with a regression test, and moving its row to "Closed" with the commit.

### From the Pi bring-up (2026-11-20)

| ID | Severity | Blocks | Where | Problem | Agreed fix |
|---|---|---|---|---|---|
| P2 | Low | — | the Pi's clock | The Pi 5's RTC has no battery fitted, and with the overlay on, timesyncd's saved clock (`/var/lib/systemd/timesync/clock`) is written to RAM only. After a real power cut, the Pi boots with a stale time until the first NTP sync. Since `0d4d0b5` (verified on the Pi 2026-11-21) every `atlas-*.service` waits for `time-sync.target` and `systemd-time-wait-sync` gives up after 90 s, so ATLAS only starts on a stale clock when the Pi has no internet for those 90 s; the failed wait then shows in `systemctl --failed`. | **Still to do (owner, hardware):** fit the RTC battery, so the clock is right even when the Pi boots offline after a power cut. Software side done: see the step 11 maintenance-window row in `docs/runbooks/pi-bringup.md` Results. |
| P3 | Medium | — | `/boot/firmware` (FAT); `deploy/provisioning/base-os.sh` | Raspberry Pi Imager writes the admin's password hash into `/boot/firmware/user-data` (`passwd:`), and the FAT partition is mounted with `fmask=0022`, so **every local user can read it**: checked 2026-11-21 as `atlas-egress` inside its running sandbox, as `nobody` and as `joe`. It is the password `sudo` asks for. A compromised service could crack it offline. Cloud-init's copy (`/var/lib/cloud/instances/*/user-data.txt`) and `/etc/shadow` are root-only. | Agreed 2026-11-22; **fixed in `base-os.sh`, not yet applied on the Pi.** `apply` sets `fmask=0077,dmask=0077` on the `/boot/firmware` fstab line, disables cloud-init (`/etc/cloud/cloud-init.disabled`), removes every line holding a password hash from the seed on the boot partition, from `/var/lib/cloud` and from cloud-init's logs (binary state files holding one are deleted), and deletes macOS metadata from the boot partition (the Spotlight index there had indexed `user-data`). `check` verifies the fstab and live mount options, that `nobody` can't read `config.txt`, that cloud-init is disabled, and that no copy of a hash or macOS metadata is left. **Still to do:** a maintenance window on the Pi (overlay off, `apply`, overlay on, reboot, `check`). Until then: use a password for `joe` that isn't used anywhere else. |
