## 1. Wake claims after a cold boot

**Problem.** `WakeClaim.first_packet_at` accepts a claim only if "the last resume happened after this time". A Wake-on-LAN from full shutdown (S5) is a boot, not a resume, so `last_resume_at` is null. hostd would then refuse every sleep request with `not_atlas_woken`, and ATLAS could never put back to sleep a host it had cold-booted.

There is a second gap: the rule has no upper bound. A resume hours after a failed wake attempt would still match that old claim.

**Change.**

- Add `PowerInfo.booted_at` (required, `date-time`): when the OS last booted.
- Define the **wake-cycle start** as `last_resume_at` if there has been a resume since boot, otherwise `booted_at`.
- `PowerInfo.last_wake_source` describes the wake-cycle start: the last resume, or the boot if there has been no resume. When Windows records no source for a cold boot, it is `unknown`.
- `WakeClaim` acceptance rule, replacing the current description:

  > hostd accepts the claim only if all of these hold:
  > - `first_packet_at − 5 s ≤ wake-cycle start ≤ first_packet_at + 90 s`;
  > - `last_wake_source` is `network` or `unknown`.
  >
  > Otherwise the claim is inconsistent, and the request is refused with `not_atlas_woken` (unless the owner has opted in to sleeping user-woken hosts).

**Why 90 s:** the Pi gives up on a wake after 60 s (§5.4, CT-1..4). A cold boot that only starts more than 90 s after the first packet wasn't caused by that wake.

**Residual risk.** On a cold boot, Windows often records the wake source as `unknown`. If you press the power button within that 90 s window, hostd could take the boot for an ATLAS wake. The other refusal reasons still protect you if you're actually using the machine: `user_input_recent`, `fullscreen_app` and `resume_grace`. The worst case is that ATLAS sleeps a host you turned on and then left idle. OW-1 (unexpected-wake alerting) is unaffected.

**Change for agent B:** B already treats the boot as the cycle start. It still needs to add the 90 s upper bound and expose `booted_at`.

## 2. No usable sleep state

**Problem.** `PowerInfo.preferred_sleep_state` is required and has no value for "none". When `powercfg /a` offers no usable state, hostd currently reports `hibernate` as a placeholder, which is false.

**Change.** Make `preferred_sleep_state` nullable (`oneOf: [SleepState, null]`). It is null exactly when `sleep_states_available` is empty, and then `sleep_eligibility.reasons` contains `sleep_unsupported`.

**Change for agent B:** report `null` instead of the placeholder.

## 3. Error responses the spec doesn't list

**Problem.** hostd needs error responses that 1.0.0 doesn't describe: oversized bodies, the lease limit, unknown routes, wrong methods, internal failures and malformed lease IDs.

**Change.**

- Add a `default` response (schema `Error`) to every operation. It covers 404 `NOT_FOUND` and 405 `METHOD_NOT_ALLOWED` for unknown routes and methods, and 500 `INTERNAL_ERROR` for unexpected failures. Use 500, not 503: 503 tells the Pi to retry, and an internal error isn't a temporary condition. The one 503 in the spec (`/v1/gpu`, `NVML_UNAVAILABLE`) keeps its meaning.
- Under the existing 400 `BadRequest`:
  - `BODY_TOO_LARGE`: the body exceeds hostd's limit (4 KiB);
  - `LEASE_LIMIT`: a PUT would create a 17th lease (the `Status.leases` limit is 16);
  - `INVALID_LEASE_ID`: the `lease_id` path parameter doesn't match `Id`, on both PUT and DELETE. A DELETE of a well-formed lease ID that doesn't exist remains a 204 no-op.
- Add these codes to the hostd row of the code catalogue in `contracts/README.md`: `BODY_TOO_LARGE`, `LEASE_LIMIT`, `INVALID_LEASE_ID`, `NOT_FOUND`, `METHOD_NOT_ALLOWED`, `INTERNAL_ERROR`.

**Change for agent B:**

- Return 500 instead of 503 for `INTERNAL_ERROR`.
- Return 400 `INVALID_LEASE_ID` for a malformed lease ID, instead of 204 on DELETE.
- `BODY_TOO_LARGE`, `LEASE_LIMIT`, 404 and 405 already match.

## 4. Clarifications (descriptions only)

- **`GpuReport.llm_server_vram_mb` / `foreign_vram_mb`:** under WDDM, NVML often reports no per-process memory. In that case `llm_server_vram_mb` is 0 and `foreign_vram_mb` is all used VRAM. `vram_free_mb` is always authoritative, and it's the only VRAM field the Pi acts on.
- **`ActivityReport.foreign_gpu_busy`:** true if a non-LLM process is above the hostd per-process GPU threshold, or if total GPU utilisation is at or above `sleep.foreign_gpu_util_pct` (hostd config, default 30) while the LLM server is idle.

## Not changed

- **`boot_id`** stays "changes on every OS boot, not on resume". Agent B's minute-rounded uptime-counter implementation has to be checked against that on the Windows desktop (`hostd/README.md`, Windows test checklist). If it fails, the implementation changes, not the contract.
- **Hosting method** for the service is a Phase 1 decision, outside the contract.
- **`allow_sleep_if_user_woke`** is hostd configuration and defaults to false.
